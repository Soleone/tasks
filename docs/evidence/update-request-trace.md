# One task.update request (`mg8`, 2026-10-04)

This traces the existing content update, not a new API or writer framework. The browser editor and actual JSON-lines process proofs reach the same gateway/writer. Native editor launch remains unimplemented. No commands, canonical format, cache schema or durability guarantees changed.

## Concrete request

In a disposable golden workspace, select task `c8d4206d-c25a-4317-baa4-a2c5443060e9` and edit its title to `Call @alice`. Keep the context and positive version returned by the selected backend. The frontend sends a literal title, not shorthand classification. Tests also send `" Call @alice "` directly to demonstrate normalization without changing original-request identity.

1. **Prepare, once.** `V2EditorClient.begin(id)` checks ready state and advertised command, then reads that task under the same context. `prepare(baseline, content)` includes its ID/version, literal title and changed content fields. `V2PreparedEdit` serializes one executing envelope with a fresh key/correlation ID, actor and false read-only/dry-run flags; it freezes the root/cache/profile selection. Execution reuses that serialization. Preview makes a separate dry-run/keyless copy and cannot renew an already-attempted execution.
2. **Decode the boundary.** `executeV2Line`/`parseV2Request` validate the envelope. The gateway's `isV2TaskEditRequest` narrows only the three existing single-file edit families. Inside the writer, root locking and context/key checks precede `decodeV2TaskEdit`. Content parsing returns `V2UpdateInput`: safe task ID, positive expected version and a typed content patch. Status/relationship neighbors have separate discriminated inputs; no nullable-input fallback chooses an effect. Unsupported content fields never reach the domain.
3. **Do not normalize retry identity.** The raw envelope remains separate from the decoded patch. `v2RequestIdentity` hashes version, command, original args, actor, context and flags, not correlation ID. Trimming a title or normalizing tags does not silently rewrite this identity. A matching receipt is checked before live task/graph checks. It can report historical success after a target disappears, but cannot recreate it. The task-result decoder validates cached JSON before treating it as typed success.
4. **Compute one effect.** Without a receipt, pending evidence blocks a new write. A complete canonical read supplies the live task and authority; expected version must match. `applyV2Update` overlays only the allowed content patch. A meaningful change updates edit time but preserves closure, relationships, order and unrelated fields. Preview returns a typed nonexecuting projection. Executed no-op stores a `changed:false` receipt, with no operation/history or canonical replacement.
5. **Publish recovery authority before bytes.** A meaningful update fixes one operation ID/time, original request, physical root/cache binding, exact before/next bytes and full file guards. `guardV2Update` validates the intended effect. Directory synchronization and `persistV2Pending` durably publish that intent before any task replacement. Failures leave inspectable evidence rather than generating another request.
6. **Replace, verify, then commit.** `applyV2Journal` checks guarded membership/bytes/physical ownership, writes and flushes a temporary task file, replaces the target and flushes its directory. Already-replaced recovery must reflush that directory even when no rewrite is needed. A complete verified snapshot reaches `commitV2Update`, which records the fixed history/effect and typed `changed:true` result with its operation ID. It stores an original-request receipt only if the original context is still authoritative. SQLite commits before pending intent retirement, never after it.
7. **Handle uncertainty explicitly.** Lost reply means retry the identical original envelope, not a new key or version. Before commit, the pending intent requires explicit `workspace.recovery.resume`; recovery reproduces the fixed bytes/time and commits the original effect once. After commit, a valid original receipt allows cleanup without a second effect. The recovery acknowledgment has its own key/receipt. Cache loss permits explicit guarded recovery but cannot restore old-context replay authority. Root/cache/profile selection must not change during uncertainty.

## What was simplified and typed

- Removed the writer's `contentInput ?? relationshipInput ?? statusInput` and nested effect-selection expressions. The decoder and exhaustive effect switch represent the actual existing three families; no generic engine, service interfaces or command-wide redesign.
- `V2TaskEditRequest` excludes creation, undo and workspace controls from this replacement writer. `V2UpdateIntent` retains that concrete original request. Existing command allowlists remain unchanged.
- Execution results distinguish changed success with required operation identity from no-op without one. Preview results have explicit nonexecution flags and no operation. Unknown task-result JSON is validated at frontend/receipt boundaries; the existing frontend projection parser moved to their shared pure decoder, without a compatibility export.
- Invalid retained receipt shape returns `INVALID_STORAGE`. It cannot create an effect, retire pending evidence or consume the recovery acknowledgment key. Tests restore only their synthetic corrupted cache row and verify the same original request/recovery key can complete.
- Kept the distinct creation/deletion safeguards and deferred `v2CopyStage.ts`, general envelope/query typing, doctor/purge/order and native launch. Clean-code checklist found no unrelated changes or future hooks; the receipt catch specifically handles invalid decoded cache results.
